# 1. 소개 (Introduction)

이 문서는 **weaver2에 처음 투입된 개발자**가 코드를 만지기 전에 읽는 온보딩 가이드의 첫 장입니다. 목표는 단 하나 — weaver2가 *무엇이고, 왜 이렇게 생겼으며, 어디서부터 봐야 하는지*에 대한 **멘탈모델**을 먼저 머릿속에 세우는 것입니다.

개별 기능이나 API가 궁금하다면 [`README.md`](../../README.md)가, 설계 결정의 이유가 궁금하다면 [`CHARTER.md`](../../CHARTER.md)가 이미 잘 답해 줍니다. 이 가이드는 그 사이의 빈 공간 — **"처음 보는 사람이 따라 읽으며 전체 그림을 잡는 흐름"** — 을 채웁니다.

---

## 이 가이드를 읽기 전에 — 기존 문서와의 관계

weaver2에는 이미 문서가 여럿 있습니다. 헷갈리지 않도록 역할을 먼저 구분합니다.

| 문서 | 성격 | 언제 보나 |
|------|------|----------|
| **이 온보딩 가이드** (`docs/onboarding/`) | 내러티브 · 학습용 | **처음 투입됐을 때, 순서대로 통독** |
| [`README.md`](../../README.md) | 레퍼런스 (기능 카탈로그·API·명령어) | "그 기능/엔드포인트 뭐였지?" 찾을 때 |
| [`CHARTER.md`](../../CHARTER.md) | 헌장 (설계 의도·범위·원칙) | "이건 왜 이렇게 짰지?" 물을 때 |
| [`CONTRIBUTING.md`](../../CONTRIBUTING.md) | 워크플로우 (브랜치·커밋·PR·리뷰) | 실제로 코드를 올릴 때 |
| [`CLAUDE.md`](../../CLAUDE.md) | 코딩 철학·금지 사항 (AI 협업 규칙 포함) | 코드 스타일·규칙을 확인할 때 |

> **왜 이 가이드가 따로 필요한가?**
> weaver2는 원래 **"본인용"** 보일러플레이트로 출발했습니다. 그래서 기존 문서는 압축적이고, 맥락을 이미 아는 사람을 전제했죠. 하지만 이제 **사내 팀이 함께 만지는 공용 기반**으로 전환됐고(`CHARTER.md §2`), 새로 합류한 동료에게는 그 압축된 맥락이 없습니다. **이 온보딩 가이드는 바로 그 빈 맥락을 채워 주는 문서**입니다.

## 1.1 weaver2란?

weaver2는 **NestJS + Next.js 기반의 커뮤니티 플랫폼 보일러플레이트**입니다.

여기서 가장 중요한 단어는 **"보일러플레이트"**입니다. weaver2는 그 자체로 완성된 *제품*이 아니라, **새 프로젝트를 시작할 때마다 매번 다시 짓기 귀찮은 공통 기반을 미리 깎아 둔 출발선**입니다.

커뮤니티 서비스를 새로 만든다고 하면, 비즈니스 로직(예: 우리만의 특별한 기능)에 앞서 항상 똑같은 것들을 또 만들어야 합니다.

- 회원가입 / 로그인 / 소셜 로그인 / 2단계 인증
- 권한·역할 관리
- 게시판 / 댓글 / 첨부파일 / 검색
- 알림 (실시간·푸시)
- 신고·제재 (모더레이션)
- 관리자 페이지

weaver2는 **이 공통 기반을 이미 다 갖춘 상태**에서 시작합니다. `CHARTER.md §1`의 표현을 빌리면, *"공통 기반을 매번 다시 짓지 않고, 새 프로젝트가 비즈니스 로직에만 집중할 수 있도록 출발선을 깎아 둔다"*는 것이 weaver2의 존재 이유입니다.

> ### 📦 보일러플레이트 vs 프레임워크 — 헷갈리지 말 것
>
> 가장 먼저 못 박을 것 하나. **weaver2는 프레임워크가 아닙니다.** NestJS·Next.js라는 *진짜 프레임워크 위에 세워진 완성된 애플리케이션*을, 새 프로젝트의 출발선으로 통째로 건네주는 **보일러플레이트(스타터)**입니다.
>
> | 기준 | 프레임워크 (NestJS 등) | 보일러플레이트 (weaver2) |
> |------|----------------------|------------------------|
> | **제어 흐름** | *내 코드를 호출*한다 (IoC) | 호출 골격이 아니다 |
> | **소유권** | 의존성으로 *가져다 쓴다* (`npm install`) | fork하면 *내 코드가 된다* |
> | **수정** | 직접 고치지 않는다 | 시드·권한·스킨을 *직접 고친다* |
>
> 프레임워크가 *빈 골격*을 준다면, weaver2는 *이미 다 채워진 집*을 주고 "여기서 시작해서 네 색깔로 바꿔"라고 합니다.
>
> ⚠️ **단, 그 집 안에서 일할 땐 프레임워크처럼 규약을 따라야 합니다** — 정해진 4계층, `Controller→Service→Repository`, 권한 패턴, `ApiClient` 강제 등. 게다가 `module-registry`(8장)라는 자체 조립 도구까지 갖춰, 보통의 보일러플레이트보다 규율이 셉니다. 그래서 *체감*은 "내부 프레임워크"에 가깝지만, **분류상으로는 보일러플레이트**입니다. 이 차이를 첫 단추에 잡아 두면 이후가 안 어긋납니다.

### "제품이 아니다"가 코드에 남긴 흔적

weaver2가 *재사용용 출발선*이라는 사실은 단순한 설명이 아니라, **코드 구조 곳곳에 직접 영향을 줍니다.** 이걸 모르면 "왜 이렇게까지 복잡하게 짰지?"라는 인상을 받기 쉽습니다.

- 기능들이 **잘라내고 붙이기 쉽게** 분리되어 있습니다 → 이것이 [8장 모듈 레지스트리](08-module-registry.md)의 배경입니다.
- 갈아끼울 지점이 **환경변수·토큰으로 추상화**되어 있습니다 (예: 파일 저장을 `local` ↔ `s3`로 전환하는 `STORAGE_DRIVER`).
- 프로젝트별로 바꿔야 할 곳이 [`CHARTER.md §9 분기 체크리스트`](../../CHARTER.md)에 명시되어 있습니다.

> 📌 **기억할 것**: weaver2의 많은 복잡함은 "범용 보일러플레이트로서 깔끔하게 분리·교체되기 위한" 비용입니다. 일반적인 단일 서비스 코드보다 추상화가 한 겹 더 있다고 생각하면 됩니다.

## 1.2 핵심 개념과 멘탈모델

코드를 열기 전에, weaver2를 **하나의 지도**로 머릿속에 그려 둡시다. 세부 사항은 이후 각 장에서 다루므로, 지금은 "이런 덩어리들이 이렇게 연결돼 있구나" 정도만 잡으면 충분합니다.

### ① 모노레포 — 한 저장소, 여러 패키지

weaver2는 **pnpm 모노레포**입니다. 하나의 저장소 안에 실행되는 앱(`apps/`)과 공유 라이브러리(`libs/`)가 함께 들어 있습니다.

```
weaver2/
├── apps/
│   ├── core-backend/    # NestJS API 서버 (port 4000)
│   └── core-frontend/   # Next.js 웹 앱 (port 3000)
└── libs/                # 백·프론트가 공유하는 패키지들
    ├── common/          # 전역 데코레이터·인터셉터·필터
    ├── email/           # 메일 발송 래퍼
    ├── pagination/      # Keyset 페이지네이션
    ├── prisma/          # PrismaService 모듈
    ├── shared/          # 권한 상수 (백·프론트 공용) ★
    └── upload/          # 파일 저장 (Local/S3)
```

가장 눈여겨볼 것은 **`libs/shared`**입니다. 권한 정의(`PERMISSIONS` 상수)처럼 **백엔드와 프론트엔드가 똑같이 알아야 하는 것**을 한곳에 두어, 양쪽이 import해서 공유합니다. "권한의 진실은 한 곳에만 있다"가 모노레포 구조의 핵심 이유입니다.

### ② 백엔드 4계층 — 코드가 사는 동네

백엔드(`apps/core-backend/src/`)는 기능을 성격에 따라 네 동네로 나눕니다.

| 계층 | 무엇이 사나 | 예 |
|------|------------|-----|
| `core/` | **프레임워크급 기반 기능** | auth, user, notification, permission, terms |
| `features/` | **비즈니스 기능** | board(게시판), report(신고), search, banner |
| `infrastructure/` | **인프라·외부 연동** | email, upload, config |
| `system/` | **관리자 API** | admin 전용 엔드포인트 |

> 새 기능을 추가할 때 "이건 어느 동네에 두지?"의 답은 대개 **`features/`**입니다. `core/`는 인증·권한처럼 모든 기능이 의존하는 토대이고, 함부로 건드리지 않습니다.

### ③ 요청의 생애 — Controller → Service → Repository

하나의 API 요청이 처리되는 길은 항상 같은 모양입니다.

```
HTTP 요청
  → Controller   (입구: 경로·검증·인증)
  → Service       (두뇌: 비즈니스 로직)
  → Repository    (손발: DB 접근)
      ├─ *.query.ts    (읽기)
      └─ *.command.ts  (쓰기)
  → Prisma → PostgreSQL
```

특이한 점은 **Repository를 읽기(`*.query.ts`)와 쓰기(`*.command.ts`) 파일로 분리**한다는 것입니다. `CHARTER.md §5`는 이를 *"읽기/쓰기 책임을 파일 레벨에서 시각화"*하기 위한 의도라고 설명합니다. 자세한 추적은 [3장 백엔드 핵심](03-backend-fundamentals.md)에서 실제 예시로 따라갑니다.

### ④ 권한 — 역할(Role)이 아니라 권한 그룹(PermissionGroup)

weaver2는 흔한 "관리자/일반회원" 같은 **역할(Role) 방식을 쓰지 않습니다.** 대신 **권한 그룹 + 와일드카드** 방식을 씁니다 (AWS IAM과 비슷한 발상).

- 사용자는 여러 **권한 그룹**에 속할 수 있습니다 (시드 기준 6종: SuperAdmin / Admin / Operator / Moderator / User / Suspended).
- 권한은 `board:read`, `board:write` 같은 문자열이며, **`board:*` 와일드카드**로 묶을 수 있습니다.
- 그 정의(`PERMISSIONS`)와 검사 함수(`hasPermission()`)가 `libs/shared`에 있어 **백·프론트가 공유**합니다.

자세히는 [5장 인증과 권한](05-auth-and-permissions.md)에서 다룹니다.

### ⑤ 곁다리지만 알아두면 좋은 것

- **알림**: 이벤트(`notification.created`)가 발생하면 → DB 저장 + **SSE 실시간 전송** + **웹 푸시(VAPID)**로 흘러갑니다. `NOTIFICATION_EMITTER` 토큰으로 추상화돼 있어 나중에 Redis 기반으로 교체할 수 있습니다.
- **파일 저장**: `STORAGE_DRIVER` 환경변수 하나로 로컬 디스크 ↔ S3(MinIO 호환)를 전환합니다.
- **보안 기본값**: 모든 엔드포인트는 **기본적으로 보호**되고, 공개가 필요한 곳에만 `@Public`을 명시합니다 (secure-by-default).

### ⑥ 이 브랜치의 본체 — 모듈 레지스트리 (module-registry)

지금 보고 있는 `feat/module-registry` 브랜치에는 weaver2의 **가장 독특하고 새로운 개념**이 들어 있습니다. README에는 아직 설명이 없으니, 처음 보면 `catalog/`, `scripts/module/`, `libs/module-registry/`의 정체를 알기 어렵습니다.

한 문장으로 요약하면 — **"하나의 기능(예: 게시판)을 백엔드·프론트·DB 스키마·시드·권한·라우트에 걸쳐 흩어진 모든 조각까지 묶어서, 통째로 잘라내고 다시 붙일 수 있게 만드는 시스템"**입니다.

여기서 미리 잡아 둘 핵심 직관 하나:

> 🧩 **weaver2에서 "기능 하나"는 한 폴더에 모여 있지 않습니다.** 게시판 기능은 백엔드 모듈, 관리자 메뉴, 권한 정의, 시드 데이터, 사이드바 등록, DB 스키마 등 **7~8곳에 흩어져** 있습니다. 모듈 레지스트리는 이 흩어진 지점들을 매니페스트(`*.feature.ts`)로 선언해 추적·관리합니다.

이 개념은 weaver2를 이해하는 데 매우 중요하지만 분량도 크므로, **이 가이드의 [8장 전체](08-module-registry.md)**를 여기에 할애합니다. 지금은 *"한 기능이 여러 곳에 흩어져 있고, 그걸 묶어 다루는 장치가 있다"*는 것만 기억하면 됩니다.

## 1.3 기술 스택 개요

weaver2가 어떤 기술 위에 서 있는지, 그리고 **왜 그걸 골랐는지**를 함께 봅니다. 선택의 이유를 알면 코드가 훨씬 잘 읽힙니다.

| 영역 | 기술 | 선택 이유 (요약) |
|------|------|------------------|
| Backend | **NestJS** + TypeScript | 모듈·DI 기반 구조화. 대규모 기능을 일관된 패턴으로 |
| Frontend | **Next.js 16** (App Router) + Tailwind | App Router 기반 풀스택 React |
| Database | **PostgreSQL** + **Prisma ORM** | 타입 안전한 스키마·마이그레이션 |
| 인증 | **JWT (HttpOnly Cookie)**, native OAuth | **소셜 OAuth는 Passport 전략 미사용**(native 직접 구현) — 블랙박스를 줄여 디버깅 가능하게. *(단 JWT·로컬 로그인 인증은 `passport-jwt`/`passport-local` 사용)* |
| 실시간 | **SSE** + Web Push (VAPID) | 단방향 알림엔 SSE로 충분 → WebSocket 인프라 회피 |
| 저장소 | Local / **AWS S3**(MinIO) | `STORAGE_DRIVER` env로 전환 |
| 이메일 | Nodemailer (SMTP) | DB 템플릿 관리·발송 로그 |
| 문서 | Swagger / OpenAPI | `http://localhost:4000/docs` |
| 품질 | ESLint · Prettier · Husky | pre-commit 검사 |

특별히 기억해 둘 **"weaver2다운" 선택** 네 가지 (모두 `CHARTER.md §5`의 설계 원칙):

1. **소셜 OAuth에 Passport 전략을 안 쓴다** — Google/Kakao/Naver를 native로 직접 구현(블랙박스 대신 디버깅 가능성). *단 JWT·로컬 인증 자체는 `passport-jwt`/`passport-local`을 씁니다 — "Passport를 전혀 안 쓴다"가 아니라 "소셜 OAuth 전략만 직접 짠다"가 정확합니다.*
2. **WebSocket을 안 쓴다** — 알림은 SSE + Web Push. 단방향이면 충분하니 인프라를 줄임.
3. **모노레포 + `libs/shared`** — 권한 정의를 백·프론트가 한 곳에서 공유.
4. **CQRS 파일 분리** — Repository를 `*.query.ts`(읽기) / `*.command.ts`(쓰기)로 나눔.

> 순수 NestJS·Next.js·Prisma 문법 자체는 이 가이드에서 다시 설명하지 않습니다. 그건 각 프레임워크 [공식 문서](https://docs.nestjs.com)가 가장 정확합니다. 이 가이드는 **"weaver2가 그것들을 *어떻게* 쓰는지"**에 집중합니다.
>
> 📚 **엮어둔 스택 전체 목록**과 **무엇을 어떤 순서로 배울지**(공식 문서 링크 포함)는 → **[기술 스택 & 학습 로드맵](tech-stack.md)**에 따로 정리돼 있습니다. "이름 그대로 *엮어(weave)* 둔 것들"이 한눈에 보여요.
